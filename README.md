# Fraud Detection on a Highly Imbalanced, Privacy-Preserving Benchmark (BAF)

**Author:** Shadi Nayyeri

## Project Overview

This repository contains a machine learning pipeline that detects fraudulent bank account opening applications using the **Bank Account Fraud (BAF) Dataset Suite**. Fraud makes up only about 1% of applications, so the project focuses on three questions:

1. How well can a gradient-boosting model rank fraudulent applications above legitimate ones?
2. How does the choice of decision threshold change the trade-off between fraud caught (recall) and legitimate customers wrongly flagged (false positive rate)?
3. Does the model treat age, income and employment-status groups equally in terms of false alarms?

Everything is in one notebook: `baf_predictive_modeling.ipynb`.

## Dataset

The BAF suite was created by researchers at **Feedzai** and **Universidade do Porto** (NeurIPS 2022, Datasets and Benchmarks track) to stress-test ML and fair-ML methods under realistic conditions.

- **Size:** 6 datasets (a *Base* variant and 5 bias variants) of 1 million applications each. This project uses the **Base** variant, in which no bias was artificially induced.
- **Synthetic data:** every row is a feature-engineered bank account application generated by a **CTGAN** trained on a real, anonymized bank account opening dataset.
- **Privacy-promoting steps** applied by the authors before and after GAN training: feature pre-selection, Laplacian noise on numeric and categorical features, categorization of age and income, label encoding of key categorical variables, and a filter removing generated rows that match an original record. The datasheet describes these as privacy-promoting interventions; it does not claim a formal differential privacy guarantee.
- **Target:** `fraud_bool` (1 = fraudulent application, 0 = legitimate).
- **Time span:** 8 months, given by the `month` column (0 to 7). The authors' protocol trains on the first six months and evaluates on the last two.
- **Intended use:** the authors state that models trained on this data should not be used directly for real-world fraud detection. It is meant for ML experimentation and evaluation.

Source: the BAF Dataset Suite Datasheet and the project repository at https://github.com/feedzai/bank-account-fraud.
Citation: Jesus et al., *Turning the Tables: Biased, Imbalanced, Dynamic Tabular Datasets for ML Evaluation*, NeurIPS 2022.

## Data Preparation

| Step | Detail |
|---|---|
| Variant used | Base (1,000,000 rows) |
| Temporal split | Train: `month <= 5`, Test: `month > 5` |
| Train set | 794,989 rows, 8,151 fraud cases (about 1.03%) |
| Test set | 205,011 rows, 2,878 fraud cases (about 1.40%) |
| Input features | 29 columns (`fraud_bool`, `customer_age` and `month` removed). LightGBM reported using 28 of them. |
| Categorical handling | Native pandas `category` dtype, passed directly to LightGBM |
| Sensitive attributes | Extracted **before** dropping `customer_age`, and used only for the fairness audit |

Sensitive groups used in the audit:

- **Older:** `customer_age >= 50`
- **Low income:** `income < 0.5` (income is released in decile form)
- **Employment-status group:** `employment_status` in `CD, CE, CF, CG`. This mapping is intended to match the BAF paper's rule of encoded value >= 3. It assumes the codes `CA` to `CG` map to 0 to 6 in order. The datasheet does not document this, so treat it as an assumption.

Exploratory analysis found no feature pair with absolute correlation above 0.8. The only pair above 0.5 was `credit_risk_score` and `proposed_credit_limit` (0.61).

## Model and Methodology

**Model:** LightGBM (`LGBMClassifier`).

1. **Baseline** with class weighting (`is_unbalance=True`, 200 trees, learning rate 0.05).
2. **Hyperparameter search** with Optuna: 20 Bayesian trials, 3-fold stratified cross-validation on the training months, objective ROC-AUC. Search space: `n_estimators` 100 to 300, `learning_rate` 0.01 to 0.1 (log scale), `num_leaves` 20 to 100, `max_depth` 3 to 10. `is_unbalance` was set to `False` so the model outputs unweighted probabilities that can be thresholded manually.
3. **Final model** trained on all training months with the best trial (trial 16, cross-validated AUC 0.8962): `n_estimators=246`, `learning_rate=0.0951`, `num_leaves=86`, `max_depth=3`.
4. **Threshold selection** on the predicted fraud probability, using two strategies (see Results).
5. **Fairness audit** comparing false positive rates across groups at the 5% FPR operating point.

## Results

### Baseline (class-weighted model, test months)

ROC-AUC: **0.8863**.

| Threshold | Recall | Precision | Legitimate applications flagged |
|---|---|---|---|
| 0.5 (default `predict`) | 80% | 6% | 38,589 of 202,133 (19.1%) |
| 0.1 (manual) | 96% | 2% | 110,066 of 202,133 (54.5%) |

A high AUC does not make a model usable. Even the default threshold flags nearly one in five legitimate applications, and lowering it raises recall only at an unworkable review cost. Note that thresholds are specific to each model's probability scale: the class-weighted baseline and the tuned model produce different probabilities, so their thresholds are not comparable.

### Tuned model: two operating points (test months)

| Strategy | Threshold | FPR | Recall | Precision | F1 |
|---|---|---|---|---|---|
| **Aggressive**: 5% FPR (BAF paper's evaluation convention) | 0.0442 | 5% | **54.79%** | not computed | not computed |
| **Balanced**: maximum F1 | 0.1226 | about 1.25% | **30.02%** | 25.43% | 0.2754 |

Interpretation:

- **Aggressive:** catches a little over half of the fraud but flags up to 5% of legitimate applicants (roughly 10,100 of 202,133 test applications).
- **Balanced:** flags far fewer legitimate customers (roughly 2,500) but misses about 70% of fraud.
- Which one is right depends on the relative cost of a missed fraud versus a falsely flagged customer.

### Fairness audit (5% global FPR threshold, test months)

Metric: predictive equality, the ratio of false positive rates between the group and its complement.

| Group | FPR (in group) | FPR (rest) | Ratio |
|---|---|---|---|
| Age >= 50 | 9.78% | 4.05% | **2.41** |
| Low income | 2.08% | 6.11% | 0.34 |
| Employment-status group (CD to CG) | 0.55% | 5.39% | 0.10 |

Legitimate applicants aged 50 or older are flagged about 2.4 times as often as younger ones, even though `customer_age` was removed from the model's inputs, so other features act as proxies. The datasheet notes that the older group has roughly twice the fraud prevalence, which may contribute, but this notebook does not test that. The other two groups are flagged less often than their complements.

## Limitations

- **Thresholds were selected on the test months.** Both the 5% FPR and the max-F1 thresholds are computed from test labels, so the reported recall values are optimistic. A cleaner setup would choose thresholds on a validation window of the training months.
- **Cross-validation during tuning is random, not temporal**, even though the final evaluation is temporal.
- The max-F1 FPR is read from the ROC point nearest to the chosen threshold, so it is approximate.
- With `max_depth=3`, a tree has at most 8 leaves, so `num_leaves=86` has no practical effect.
- Single variant (Base), single random seed, and no confidence intervals.
- The fairness audit covers false positive rate at one threshold only, and group sizes are not reported.
- The data is synthetic. Results show relative behaviour on this benchmark and must not be read as real-world fraud performance.

## Reproducing

1. Download the BAF suite from the Feedzai repository (https://github.com/feedzai/bank-account-fraud) or Kaggle.
2. The notebook was written for Google Colab and reads the CSVs from `/content/drive/MyDrive/BAF_Project/archive/*.csv`. Adjust `data_paths` to your location.
3. Install dependencies with `pip install -r requirements.txt`.
